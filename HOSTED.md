# Hosted Calendar Services vs. This Project's Own Sync Model

## Summary

This repo's `data/events.json` → `scripts/sync_calendar.py` → `static/events.ics` pipeline is built around one specific idea: each event carries a **stable, human-assigned `id`** that becomes the ICS `UID`, so a future smarter sync could recognize "this is the same event, just edited" across runs (see `data/events.json`'s `_schema.id` comment and `scripts/sync_calendar.py`'s module docstring). This research asks whether any *hosted* calendar service's own API already matches that upsert-by-your-own-id shape, well enough to sit under the existing FullCalendar frontend (a public ICS feed) or replace it outright (a good native public calendar view).

**Bottom line across all candidates investigated:**

- **CalDAV (RFC 4791) is the only one of the four categories that is a *specification*, not a product**, and it is the closest structural match to this project's own model: a calendar object resource is addressed by a URL you (the client) choose, and `PUT` to that URL is create-or-replace — genuine idempotent upsert, confirmed directly in the RFC text (Section 5.3.2). The RFC additionally requires the iCalendar `UID` to be unique within a calendar collection (Section 4.1), which is the closer analog to this project's `id`. But RFC 4791 is silent on public/unauthenticated read access — CalDAV itself is authenticated-only, so whether a given server supports (a) a public ICS feed or (b) a public calendar view is entirely a *server implementation* question, not something the protocol guarantees. Of the servers checked, **Nextcloud Calendar** is the strongest fit — it documents a public read-only calendar link with its own view (b) that also offers a subscription/export link off the same page (a). Radicale and Baïkal are protocol-only with no confirmed public-feed or public-view story from their own docs.
- **Google Calendar API's `events.import`** (keyed on `iCalUID`) remains **not explicitly confirmed either way** by Google's own docs on repeated-call behavior, same as the prior research in `docs/research/google-calendar-csv-import.md` found — but this round dug further into the field semantics and found textual evidence that leans toward **NOT** being a self-deduping upsert: Google's own docs normalize multiple Event resources sharing one `iCalUID` (that's literally how recurring-series occurrences work), document uniqueness only for `id` (never for `iCalUID`), and still point developers at `events.list` filtered by `iCalUID` as the tool for finding an existing event before deciding whether to insert or update — which would be redundant advice if `import` already self-deduped. Supports (a) implicitly (Google Calendar itself has public-calendar sharing) and, less directly, (b) via Google's own public-calendar embed.
- **Teamup Calendar** is the strongest **purpose-built** match found: it documents a `remote_id` field for linking events to identifiers in third-party applications, and its Update-an-event endpoint supports addressing an event by `remote_id` (paired with `ristart_dt`) rather than only Teamup's own internal id. It supports **both (a)** a public, read-only iCalendar feed (confirmed directly from Teamup's own KB) **and (b)** a native, no-login embeddable public calendar view (confirmed directly from Teamup's own KB), plus a single recurring-series object with an `rrule` field matching this project's schema shape. The caveat: Teamup's core API *reference* pages (apidocs.teamup.com) are a JavaScript-rendered Stoplight site that this research's tooling could not directly render — the `remote_id`/`rrule` field claims rest on search-indexed snippets of those exact pages, not a raw fetch, and are flagged accordingly below.
- **Cronofy** has the most explicit, verbatim-confirmed upsert semantics of any candidate researched — "The first request made for a `calendar_id` and `event_id` combination will create an entry in the calendar and all subsequent requests will update the details of the event" (confirmed directly) — but it fails both (a) and (b): no public ICS feed (only per-recipient tracked invite attachments) and no public calendar view (it's a sync/scheduling layer over real provider calendars, not a place with its own public page).
- **Microsoft Graph Calendar API and Zoho Calendar API are ruled out**: Microsoft Graph's `id` and `iCalUId` are both explicitly documented as read-only/server-assigned, and its `transactionId` is explicitly scoped only to retry-deduplication of a single create call, not a durable resync key. Zoho's create-event API has no client-supplied external-id field at all; only a server-generated `uid` appears in the response.

## Findings

### 1. Google Calendar API — `events.import` / `iCalUID`

Verified against Google's current docs, re-confirming and extending `docs/research/google-calendar-csv-import.md`:

- [Events: import](https://developers.google.com/workspace/calendar/api/v3/reference/events/import) still describes only: "Imports an event. This operation is used to add a private copy of an existing event to a calendar. Only events with an eventType of default may be imported." The required body fields are `end`, `iCalUID` ("Event unique identifier as defined in RFC5545."), and `start`. Nothing on this page addresses what happens on a second call with the same `iCalUID`.
- [Events resource reference](https://developers.google.com/calendar/api/v3/reference/events), `iCalUID` field, in full: "Event unique identifier as defined in RFC5545. It is used to uniquely identify events across calendaring systems and must be supplied when importing events via the import method... Note that the `iCalUID` and the `id` are not identical and only one of them should be supplied at event creation time. One difference in their semantics is that in recurring events, all occurrences of one event have different `id`s while they all share the same `iCalUID`s. To retrieve an event using its `iCalUID`, call the events.list method using the `iCalUID` parameter." Google's own model already treats "multiple distinct Event resources sharing one identical `iCalUID`" as normal — that's how a recurring series' occurrences are represented — and uniqueness is documented only for `id`, never for `iCalUID`.
- [Events: insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) documents that "the `id` must be unique per calendar" — again, no equivalent uniqueness statement exists anywhere for `iCalUID`.
- [Calendar API errors guide](https://developers.google.com/workspace/calendar/api/guides/errors) documents a 409 error reason `duplicate`, "The requested identifier already exists" / "An instance with the given ID already exists in the storage," recommending "Generate a new ID if you want to create a new instance, otherwise use the update method call." This error is textually keyed on **`id`**, not `iCalUID` — and since `import` calls don't require an `id` (Google auto-assigns one), this 409 has no natural trigger for a repeated `iCalUID` value.
- `events.list`'s `iCalUID` parameter remains documented as: "Specifies an event ID in the iCalendar format to be provided in the response... Use this if you want to search for an event by its iCalendar ID" — the only Google-documented mechanism for finding an existing event by `iCalUID` before deciding whether to insert or update. If `import` silently upserted on `iCalUID`, this list-then-branch guidance would be redundant; Google does not say it's redundant.
- **Reading, not a directly-stated fact**: taken together, this is stronger structural evidence than "fully unknown" — it points toward calling `events.import` twice with the same `iCalUID` most likely producing a **second** Event object (new auto-assigned `id`, same `iCalUID`), not an in-place update. This is inference from documented field semantics, not a sentence Google states outright — flagged again below under Open Questions, and this project should test it directly against a real calendar before ever depending on the answer.
- Google's own Calendar API release-notes page (attempted at `developers.google.com/workspace/calendar/api/release-notes`) returned HTTP 404 during this research — no changelog history could be checked for a possible past clarification.
- (a) public ICS feed / (b) public calendar view: Google Calendar itself supports both a public "From URL"-subscribable feed and its own embeddable public calendar view (per Google's own calendar-sharing docs, already covered in this repo's `docs/research/calendar-subscribe-links.md`), so if this project ever moved its source-of-truth into a Google Calendar via the API, both paths would be available — but the *upsert* question above is the load-bearing uncertainty for whether that sync could ever be safely automated and re-run.

### 2. CalDAV (RFC 4791) — the protocol itself

- [RFC 4791](https://datatracker.ietf.org/doc/html/rfc4791), Section 4.1: "Calendar object resources contained in calendar collections MUST NOT contain more than one type of calendar component," and: "The UID property value of the calendar components contained in a calendar object resource MUST be unique in the scope of the calendar collection in which they are stored." Also: "Calendar components with the same UID property value, in a given calendar collection, MUST be contained in the same calendar object resource. This ensures that all components in a recurrence 'set' are contained in the same calendar object resource." This is the RFC-level analog to this project's own `id`-per-event uniqueness rule.
- Section 5.3.2 (verified directly against [rfc-editor.org/rfc/rfc4791.html](https://www.rfc-editor.org/rfc/rfc4791.html)): "New calendar object resources MUST be created with a PUT request targeted at an unmapped URI. A PUT request targeted at a mapped URI updates an existing calendar object resource." This is a genuine create-or-replace upsert primitive, keyed on whatever URL the client chooses.
- The same section also states: "The URL for each calendar object resource is entirely arbitrary and does not need to bear a specific relationship to the calendar object resource's iCalendar properties or other metadata." So the RFC deliberately does **not** require the URL to be derived from the UID — URL-choice (Section 5.3.2) and UID-uniqueness (Section 4.1) are separate rules, even though real-world servers commonly collapse them (see below).
- Section 7.9 documents the `CALDAV:calendar-multiget` REPORT: "The request body MUST be a CALDAV:calendar-multiget XML element" containing `DAV:href` elements — i.e. CalDAV's native bulk-fetch mechanism is by URL list, not by UID directly.
- **Public/unauthenticated access is out of scope for the RFC entirely.** A full-text check of RFC 4791 for "anonymous," "public," "unauthenticated," and "subscri*" found none of these terms anywhere in the document; its access-control model (Section 6) is built on WebDAV ACL ([RFC 3744](https://datatracker.ietf.org/doc/html/rfc3744)) and assumes authenticated principals throughout. This means CalDAV's own spec gives neither (a) nor (b) — both are entirely down to what a given server chooses to build on top.
- **UID-as-filename convention**: in practice, CalDAV servers/clients commonly name each resource `<uid>.ics`, effectively making the UID the real key even though the RFC calls the URL "entirely arbitrary." This research could not pull an explicit "we name resources `<uid>.ics`" sentence verbatim from Radicale's or Baïkal's own docs directly — it's a well-established real-world convention, not one this research independently confirmed in a fetched primary source, so it's flagged as strongly-implied but unconfirmed-in-primary-text.

#### Concrete providers checked

- **Radicale** ([radicale.org/v3.html](https://radicale.org/v3.html)): CalDAV/CardDAV protocol only. Storage docs describe "a file containing the item's iCalendar... data" per resource, but no REST/JSON API and no documented public/unauthenticated ICS feed or public calendar UI of its own. Effectively ruled out for both (a) and (b) as shipped — it's infrastructure, not a hosted product with a public-facing surface.
- **Baïkal** ([sabre.io/baikal](https://sabre.io/baikal/), built on sabre/dav): ships only an admin panel, no end-user public calendar view — ruled out for (b). Its underlying sabre/dav library documents an [ICS Export Plugin](http://sabre.io/dav/ics-export-plugin/): "you can generate these exports by finding a url to your calendar, and adding `?export` at the end of the url," e.g. `http://dav.example.org/calendars/user1/mycalendar?export.` Whether this bypasses CalDAV's normal authentication (i.e. is genuinely public) is not stated on that page — deployment-dependent, not guaranteed public-by-default, so (a) is possible but not confirmed as public-by-default.
- **Nextcloud Calendar** ([docs.nextcloud.com — Calendar user manual, "Publishing a calendar"](https://docs.nextcloud.com/server/latest/user_manual/en/groupware/calendar.html)): the strongest self-hostable fit found. Direct quote: "Calendars can be published through a public link to make them viewable (read-only) to external users," and "On the public page, users are able to get the subscription link for the calendar and export the whole calendar directly." That single public page satisfies **both** (b) — a rendered, read-only public calendar view (month/week/day/list, embeddable) — **and** (a) — a subscription/export link surfaced on that same page. It's built on sabre/dav underneath, so the CalDAV PUT/UID upsert semantics above still apply to the storage layer, but no separate REST/JSON API keyed by an external id was found documented on the page checked.
- **Fastmail** ([fastmail.com/dev](https://www.fastmail.com/dev/)): "Calendars — you can access via CalDAV. We will be opening up JMAP access as well, as soon as the specification is finalized" — CalDAV only today, no calendar JMAP/REST API yet. No public/unauthenticated sharing feature found on this page; a specific Fastmail help-center CalDAV article ([fastmail.help/hc/en-us/articles/1500000278341](https://www.fastmail.help/hc/en-us/articles/1500000278341)) 404'd during this research, so Fastmail's public-sharing story could not be verified further — weakest-documented of the providers checked.
- Apple iCloud and Google Calendar both also expose CalDAV interop endpoints, but neither was deep-dived here since both already have more direct native APIs covered elsewhere in this project's research (Google's Calendar API above; Apple iCloud CalDAV was out of scope for this pass).

### 3. Teamup Calendar

- **Upsert-by-your-own-id**: per search-indexed snippets of Teamup's own API reference pages ([Create an event](https://apidocs.teamup.com/docs/api/3269d0159ae9f-create-an-event), [Update an event](https://apidocs.teamup.com/docs/api/8b5d0d1556103-update-an-event)) — direct WebFetch of these specific pages, attempted twice in this research (including via a raw-HTML grep for `remote_id`/`rrule`, which found zero matches in ~450KB of fetched HTML), could not render the underlying JS/Stoplight-rendered schema, so this claim rests on search-snippet text, not a page this research directly read. With that caveat: events are described as having a `remote_id` string field for linking Teamup events to identifiers in third-party applications, and the Update-an-event endpoint documents addressing an event via `remote_id` + `ristart_dt` as an alternative to Teamup's own internal `id`. Corroborating (but non-primary, cited only as corroboration, not as a documentation source) evidence: Teamup's own [Zapier integrations KB page](https://calendar.teamup.com/kb/teamup-integrations-powered-by-zapier/), fetched directly, confirms: "**Find Event Matching Remote ID:** Finds an event that matches Remote ID" as a documented Zapier action — i.e. Teamup's own product surface treats "look up an event by remote_id" as a first-class, named capability, which supports (without being the API schema itself) the search-snippet claim above. **Not confirmed, in either the snippets or the Zapier page**: whether repeat-calling create with the same `remote_id` auto-upserts, or whether a caller must search-then-create-or-update — the same open question this research found for Google's `iCalUID`.
- **(a) Public ICS feed — confirmed directly**: [Subscribe to Teamup iCalendar feeds](https://calendar.teamup.com/kb/subscribe-to-teamup-icalendar-feeds/) (fetched directly): "iCalendar feeds are read-only and provide a periodic automatic synchronization between the source calendar (Teamup) and another calendar application," describing "one-way read-only synchronization." For external users without direct calendar access, an administrator can create "a secure read-only link" (Settings → Sharing → Add User → Link) and generate a feed URL from that link's own Preferences → iCalendar Feeds menu — the calendar itself does not need to be fully public, only the specific share-link does.
- **(b) Public calendar view — confirmed directly for capability, not for the login-free specifics**: [The Embed Wizard](https://calendar.teamup.com/kb/the-embed-wizard/) (fetched directly) documents an extensive customizable embed: Appearance (calendar size, header, view selector, menu, sidebar, date controls, border), Date & Time (timezone, week start, start date), Calendar Views (default view, agenda/list/tiles grouping), and Other Settings (language, event display) — built around "a secure (read-only) link." The page does not, in the text this research could retrieve, explicitly state whether viewing the embed requires the visitor to log in; a separate WebSearch-only pass (not independently confirmed by direct fetch) described embeds/links as working "without requiring registration or a login," which is consistent with the read-only-link model but should be verified directly if this project ever pursues Teamup.
- **Recurrence**: a single event object with an `rrule` string field in iCal RRULE format, per the same search-snippet-sourced material as above (not independently confirmed by a direct page fetch) — if accurate, this matches this project's own "one recurring-series object, not one row per occurrence" schema shape.
- Requires a free, request-based API key: confirmed directly from [Teamup Calendar API overview](https://calendar.teamup.com/kb/api-teamup-calendar/): "Using the API it is possible to read, write, update, and delete calendar events," and "Working with the API requires an API key. You can request one for free using this form."
- **Feed subscriber count vs. plan "number of users" limit — not capped, by the consistent terminology across Teamup's own docs, though never stated as an explicit numeric guarantee.** [Subscribe to Teamup iCalendar feeds](https://calendar.teamup.com/kb/subscribe-to-teamup-icalendar-feeds/) (fetched directly) draws the relevant line itself: "Calendar users should set up their own iCalendar feeds from their own customized calendar access... External individuals (those without calendar access) should be given an iCalendar feed created from a secure, read-only link." [How to Choose Between Account Access or Calendar Links](https://calendar.teamup.com/kb/how-to-choose-between-account-access-or-calendar-links/) (fetched directly) states the plan constraint in matching terms: "Each subscription level allows a certain number of **account users**" -- account users specifically, not link-based visitors. The [pricing page](https://www.teamup.com/pricing/) lists "Account-based access" (login required, counted per-plan) and "Shareable link access" (no login, no email tied to the link) as two distinct, named features. No page fetched in this research states a numeric cap on how many people can use a shareable link or the iCalendar feed generated from one -- the absence is consistent across every page checked, not just one. **Not an explicit "unlimited" statement from Teamup**, so treat as strongly-implied-by-consistent-terminology rather than a guaranteed fact; verify directly (e.g. by asking Teamup support, or testing with a plan's stated account-user cap) before relying on it for a calendar expecting many public subscribers.

### 4. Cronofy

- **Upsert-by-your-own-id — the most explicit and directly confirmed of any candidate.** [Create or Update Event](https://docs.cronofy.com/developers/api/events/upsert-event/) — confirmed directly via two independent fetches in this research (resolving an initial PUT-vs-POST discrepancy in favor of **POST**): `POST /v1/calendars/{calendar_id}/events`, and verbatim: "The first request made for a `calendar_id` and `event_id` combination will create an entry in the calendar and all subsequent requests will update the details of the event." `event_id` is a caller-assigned field, required in the request body alongside `summary`, `start`, and `end`; optional fields include `description`, `tzid`, `location`, `recurrence`, `tags`, and others. This is the one candidate in this research where the "call it twice with the same id, does it upsert" question is answered in the provider's own words, not inferred.
- **(a) Public ICS feed — fails.** Cronofy's only ICS-related feature, [Smart ICS Calendar Invites](https://www.cronofy.com/developer/smart-ics-invites), is "Trackable ICS attachments that you can use to invite anyone to calendar events" with callback-URL-based accept/decline tracking — these are per-recipient invite attachments, not a subscribable feed of the whole calendar.
- **(b) Public calendar view — fails.** Cronofy is a scheduling/sync API layered over real provider calendars (Google/Outlook/iCloud/etc.) or, for calendars with no external counterpart, an [Application Calendar](https://docs.cronofy.com/developers/calendars-events/application-calendars/) — "a specialized type of Cronofy `Account` that automatically gets created with one `Profile` and one `Calendar`," for customers who want "to leverage the power of Cronofy's scheduling API without linking it to a 'real' calendar." Nothing in Cronofy's docs describes Application Calendars (or any calendar under Cronofy) as having a public-facing rendered view.
- Recurrence: a single event with a `recurrence` object/`rules` array in iCal-RRULE-like format, matching this project's schema shape — but documented as an **Alpha**-tier API surface (per the field's own "ALPHA" annotation on the upsert-event page), so less stable than the rest of Cronofy's API.

### 5. Ruled out (fail the upsert-by-your-own-id requirement)

- **Microsoft Graph Calendar API** — confirmed via a full direct fetch of the [Event resource reference](https://learn.microsoft.com/en-us/graph/api/resources/event): `id` is documented as "Case-sensitive and read-only," `iCalUId` as "A unique identifier for an event across calendars... Read-only," and `transactionId` as "A custom identifier specified by a client app for the server to avoid redundant POST operations in case of client retries to create the same event... After you set transactionId when creating an event, you can't change transactionId in a subsequent update." None of these three fields is a client-controlled, durable, re-usable key for a future resync — `transactionId` is explicitly scoped only to de-duplicating retries of a single create call, not to recognizing "this is the same event" across separate sync runs. Ruled out.
- **Zoho Calendar API** — per [Create event](https://www.zoho.com/calendar/help/api/post-create-event.html): the create-event request body (`eventdata` object: `title`, `dateandtime`, `isallday`, `description`, `attendees`, recurrence via `rrule`/`repeat`, etc.) has no client-supplied external-id input field anywhere; only a server-generated `uid` (e.g. `...@zoho.com`) appears in the response. Ruled out.

## Open Questions / Unverified

- **Whether Google's `events.import` is truly idempotent on repeated `iCalUID` calls is still not stated anywhere in Google's own docs** — this research's reading (leaning toward "creates a duplicate Event resource, not an update") is an inference from documented field semantics (uniqueness stated only for `id`; `events.list`-by-`iCalUID` offered as the lookup path), not a sentence Google states outright. Test directly against a real calendar before depending on this.
- **Teamup's `remote_id`/`rrule` field claims rest on search-indexed snippets of apidocs.teamup.com, not a directly-read page.** This research made two separate attempts (WebFetch and a raw-HTML grep for the literal strings) to render Teamup's JS/Stoplight-based API reference and could not get past the page shell in either case. The KB pages cited for (a) and (b) (iCalendar feeds, Embed Wizard, Zapier integrations) *were* fetched directly and their quotes above are solid; only the core API schema (create/update-event field names) is snippet-derived. Before relying on Teamup's upsert behavior for real, fetch `apidocs.teamup.com` with a tool that executes its client-side JS (e.g. a headless browser), or request their OpenAPI/Postman export directly from Teamup.
- **Whether Teamup's embed/share links require a visitor to log in** was not confirmed by a page this research could directly fetch with that specific sentence in it — only inferred from the "secure (read-only) link" framing and an unconfirmed WebSearch-only claim of "no login required."
- **The UID-as-filename convention for CalDAV** (`<uid>.ics` as the resource path) is a strong real-world pattern but was not confirmed verbatim in any primary source fetched directly in this research (Radicale's and Baïkal's own docs don't state it explicitly in the pages checked).
- **Whether sabre/dav's `?export` ICS-export mechanism (used by Baïkal) is public-by-default or still requires the normal CalDAV authentication** is not stated on the page fetched — this determines whether Baïkal could satisfy requirement (a) at all, and needs a live test against a real Baïkal deployment to resolve.
- **Fastmail's public-sharing story for CalDAV calendars** could not be verified — the specific Fastmail help article on CalDAV sharing 404'd during this research.
- **Nextcloud Calendar's REST/JSON API surface** (as opposed to CalDAV itself) for creating/updating events keyed by an external id was not found documented on the page checked in this research — Nextcloud's fit here rests entirely on its public-link publishing feature (which is well-confirmed), not on any upsert-by-external-id API.
- **Google Calendar API release notes/changelog** could not be checked for historical clarifications on `iCalUID`/`import` behavior — the expected URL (`developers.google.com/workspace/calendar/api/release-notes`) returned HTTP 404 during this research; the correct current URL for this changelog was not located.
