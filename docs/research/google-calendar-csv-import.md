# Google Calendar CSV Import Format

## Summary

As fetched directly from Google's own help pages today, **CSV import is still supported** by the current Google Calendar product — it has not been deprecated or restricted to a Google-only export format. [support.google.com/calendar/answer/37118](https://support.google.com/calendar/answer/37118?hl=en&co=GENIE.Platform%3DDesktop) states plainly: "You can import with ICS and CSV files on a computer," and documents a specific nine-column header spec (`Subject`, `Start Date`, `Start Time`, `End Date`, `End Time`, `All Day Event`, `Description`, `Location`, `Private`) with only `Subject` and `Start Date` required. That said, CSV import has real, documented limitations that make it a poor fit for an automation like this repo's: it has **no recurrence support at all** (Google's own docs say repeating events from a CSV "will be on your calendar as a series of one-time events"), no guest/attendee support, a hard 1 MB file-size ceiling, and a rigid English-only, exact-header, comma-delimited format. **ICS (iCalendar, RFC 5545)** is Google's own native export format and the one place a `RRULE` (recurrence rule) can be expressed at all in a file-import path — making it the practically better choice whenever the source data includes a recurring schedule, which every entry in `LOCATIONS.md` does. For programmatic use, however, the **Google Calendar API** (`events.insert` / `events.import`, batched up to 1,000 calls per HTTP request) is the most robust of the three paths: it supports native `RRULE` recurrence on a single event object (no manual date enumeration), and `events.import` is purpose-built for idempotent, ID-keyed syncing from an external source of truth via the RFC 5545 `iCalUID` field — a very close match to this repo's GroupMe-sync pattern of tracking a stable per-event ID. In short: CSV works today but is the weakest option here; ICS is the credible file-based path; the Calendar API is the best fit if this project is headed toward real automation rather than a one-time manual import.

## Findings

### CSV format status & column spec

- **Current support confirmed directly**: [support.google.com/calendar/answer/37118](https://support.google.com/calendar/answer/37118?hl=en&co=GENIE.Platform%3DDesktop) ("Import events to Google Calendar") states: "You can import with ICS and CSV files on a computer." No deprecation notice, beta/legacy warning, or restriction-to-Google's-own-export-format language appears anywhere on this page or on the related [Fix problems with importing](https://support.google.com/calendar/answer/45654?hl=en) page as fetched today (2026-09-25).
- **Required headers**: only `Subject` (event name) and `Start Date` are required. The page states verbatim: "The first row of your new spreadsheet includes headers like 'Subject' and 'Start Date.' To import into Google Calendar, the headers must be in English."
- **Full documented header list, in order**: `Subject` (required), `Start Date` (required), `Start Time`, `End Date`, `End Time`, `All Day Event`, `Description`, `Location`, `Private`. Any column not matching these exact (English) header names is not documented as recognized.
- **Date/time format**: dates are given in `MM/DD/YYYY` form, e.g. the page's own example value `"05/30/2020"`; times are 12-hour clock with AM/PM, e.g. `"10:00 AM"` and `"1:00 PM"`.
- **All-day vs. timed events**: distinguished by the `All Day Event` column — "If it's an all-day event, enter True. If it isn't an all-day event, enter False."
- **Timezone handling**: not documented for CSV import specifically on either page fetched. [Fix problems with importing](https://support.google.com/calendar/answer/45654?hl=en) only advises, generically, to check that "the time zone in Google Calendar matches the time zone in the original calendar application" — there is no CSV-specific timezone column or override documented.
- **Delimiter / encoding requirement**: [Fix problems with importing](https://support.google.com/calendar/answer/45654?hl=en) says to "Check that your file uses a comma as the delimiter" and explicitly: "Google Calendar doesn't work with files that use a semicolon ( ; ) or colon ( : ) to separate fields."
- **File size limit**: "Google Calendar only works with files that are one megabyte (1MB) or smaller" — this limit is stated on the Fix-problems page, not tied to a specific row count.
- **Recurrence is NOT preserved**: from [support.google.com/calendar/answer/37118](https://support.google.com/calendar/answer/37118?hl=en&co=GENIE.Platform%3DDesktop): "If you import repeat events from a .csv file, they might not show up that way. They'll be on your calendar as a series of one-time events." There is no `RRULE`-equivalent column in the documented CSV header spec — recurrence simply cannot be expressed in Google's CSV format; each occurrence must be its own row.
- **Guests/attendees and conference data are not imported** via CSV (also confirmed via the same page).
- **Import steps** (same page):
  1. On a computer, open Google Calendar.
  2. In the top right, click the gear icon → **Settings**.
  3. In the left-hand menu, click **Import & export**.
  4. Click **Select file from your computer** and choose a file ending in `.ics` or `.csv`.
  5. Choose which calendar to add the imported events to (a dropdown; defaults to the primary calendar).
  6. Click **Import**.
- Import (like export) is a **computer/desktop-web-only** feature — not available from the Google Calendar mobile app, per [support.google.com/calendar/answer/37111](https://support.google.com/calendar/answer/37111?hl=en) ("Export events from your Google Calendar"), which states export "only works on a computer, not in the Google Calendar app," and the analogous Import & export menu location is the same settings surface for both directions.

### ICS / iCalendar import (the practically recommended file-based path)

- Google Calendar's own **export** format is exclusively `.ics` — [support.google.com/calendar/answer/37111](https://support.google.com/calendar/answer/37111?hl=en) documents no CSV export option at all, only: exporting *all* calendars downloads a `.zip` of `.ics` files (Settings → **Import & export** → **Export**), and exporting a *single* calendar (hover the calendar under "My calendars" → **More** → **Settings and sharing** → **Export calendar**) downloads one `.ics` file. This asymmetry — Google exports only ICS but imports both ICS and CSV — is itself a signal that ICS is the format Google treats as canonical.
- **Import mechanics for `.ics` are identical to CSV**: same Settings → **Import & export** screen, same "Select file from your computer," same destination-calendar picker, same **Import** button ([support.google.com/calendar/answer/37118](https://support.google.com/calendar/answer/37118?hl=en&co=GENIE.Platform%3DDesktop)). The same 1 MB file-size ceiling applies ([support.google.com/calendar/answer/45654](https://support.google.com/calendar/answer/45654?hl=en); for an oversized `.ics`, Google's guidance is to re-export a shorter date range from the source application).
- **Recurrence via `RRULE` is expressible in `.ics`** (unlike CSV) because `.ics`/iCalendar is the RFC 5545 format, and Google's own developer docs tie the Calendar API's `recurrence` field directly to that spec: the Events resource's `recurrence` field is documented (per [developers.google.com/calendar/api/v3/reference/events](https://developers.google.com/calendar/api/v3/reference/events)) as "List of RRULE, EXRULE, RDATE and EXDATE lines for a recurring event, as specified in RFC5545." The formal specification itself is published by the IETF at [datatracker.ietf.org/doc/html/rfc5545](https://datatracker.ietf.org/doc/html/rfc5545) (RRULE recurrence-rule grammar is in section 3.3.10 / 3.8.5.3 of that spec).
- **Caveat on recurrence fidelity through the consumer import UI**: whether an `.ics` file's `RRULE` reliably imports as a *true single recurring series* (vs. expanding into individual one-off events) is not spelled out as an unconditional guarantee on the pages fetched. [Fix problems with importing](https://support.google.com/calendar/answer/45654?hl=en) notes only that "some calendar applications export repeating events as a collection of single events," and "because Calendar reads events as the other calendar application exported them," a source file that itself lacks a proper `RRULE` will import as one-time events — implying (but not explicitly promising) that a file with a *well-formed* `RRULE` should import as a genuine recurring series. This is flagged again under Open Questions below.

### Google Calendar API bulk-import options

Checked at [developers.google.com/calendar/api/v3/reference/events](https://developers.google.com/calendar/api/v3/reference/events) (Events resource reference) and its `insert`/`import` method pages:

- **`events.insert`** ([developers.google.com/workspace/calendar/api/guides/create-events](https://developers.google.com/workspace/calendar/api/guides/create-events)): the standard "create a new event" call. Per the guide: "The only two required fields are the `start` and `end` times." A single `events.insert` call can carry a `recurrence` array (`RRULE`/`EXRULE`/`RDATE`/`EXDATE` per RFC 5545, e.g. the guide's own example `'RRULE:FREQ=DAILY;COUNT=2'`) — meaning one API call can represent an entire recurring series without the caller having to enumerate each occurrence, unlike CSV import.
- **`events.import`** ([developers.google.com/workspace/calendar/api/v3/reference/events/import](https://developers.google.com/workspace/calendar/api/v3/reference/events/import)): "This operation is used to add a private copy of an existing event to a calendar." Key documented constraints:
  - Only events with `eventType` of `default` may be imported; importing a non-default event type converts it to `default` and drops type-specific properties.
  - The request body must supply `iCalUID` (an RFC 5545-format identifier), `start`, and `end`.
  - Per the Events-resource field reference itself: "`iCalUID`... is used to uniquely identify events across calendaring systems and must be supplied when importing events via the import method... in recurring events, all occurrences of one event have different `id`s while they all share the same `iCalUID`s" ([developers.google.com/calendar/api/v3/reference/events](https://developers.google.com/calendar/api/v3/reference/events)). This makes `events.import` naturally suited to an idempotent sync keyed by a stable external ID — directly analogous to the deterministic `source_guid` de-duplication pattern already documented for GroupMe bot posts in `docs/research/groupme-automation-interfaces.md`.
  - Required OAuth scope is one of `https://www.googleapis.com/auth/calendar`, `.../calendar.events`, `.../calendar.app.created`, or `.../calendar.events.owned`.
- **Bulk/batch mechanics**: there is no single "bulk create N events" endpoint, but the Calendar API supports **HTTP batching** ([developers.google.com/workspace/calendar/api/guides/batch](https://developers.google.com/workspace/calendar/api/guides/batch)): "The Google Calendar API supports batching, to allow your client to put several API calls into a single HTTP request," with a documented limit of "1000 calls in a single batch request." This lets an automation submit, e.g., dozens of `events.insert`/`events.import` calls (one per facility/program) in one round trip.
- **Net comparison to file import**: the API path needs no manual "Settings → Import & export" click-through, has no 1 MB file ceiling, expresses recurrence natively per event (no per-occurrence row enumeration as CSV requires), and gives a documented idempotency key (`iCalUID`) for safe re-runs — all of which make it the strongest fit for an unattended sync job, at the cost of needing OAuth credentials/a registered API project rather than just a file to click through the UI.

## Applying This to the Lacrosse Events in LOCATIONS.md

`LOCATIONS.md` entries have a consistent shape (facility/program **name**, **Link**, **Address**, **Contact**, a **Fields** indoor/outdoor tag, and a free-text **Notes** field carrying the actual schedule/day/time/cost information, e.g. "Tuesdays, 8–9 PM... Fall 2026: Sept 22 – Nov 10, 2026"). None of that schedule information is already broken into structured start/end datetimes — it's prose embedded in Notes, so **any** of the three paths above requires a parsing/normalization step first: extracting a weekday (or explicit date range), a start time, an end time, and a first/last occurrence date out of sentences like "Monday nights; ... Session starts 10/26/2026, runs through Dec 14, 2026 (8 weeks)" or "Tuesdays, 8–9 PM... Fall 2026: Sept 22 – Nov 10, 2026."

### If using CSV (works today, but must enumerate every occurrence)

Because Google's CSV format has no recurrence column, a recurring program like "Tuesdays 8–9 PM, Sept 22 – Nov 10, 2026" must become **one CSV row per Tuesday**, not one row for the series. Example built from two real `LOCATIONS.md` entries — **The Fieldhouse at Homestead Mills** adult pickup ("Tuesdays, 8–9 PM... Fall 2026: Sept 22 – Nov 10, 2026," $15/night or $80 for the 8-week session) and **NH Sportsplex — Men's Pickup Box Lacrosse** ("Monday nights 8–10 PM, $15/session"), showing only the first couple of upcoming occurrences (today is 2026-09-25) rather than all 8+ rows a real import would need:

```csv
Subject,Start Date,Start Time,End Date,End Time,All Day Event,Description,Location,Private
Adult Lacrosse Pickup - Fieldhouse at Homestead Mills,09/29/2026,08:00 PM,09/29/2026,09:00 PM,False,"Pickup-style lacrosse, adult/college/HS. $15 drop-in or $80 for the 8-week Fall session (Sept 22-Nov 10 2026). Contact: (603) 338-0064",2 South Winchester St Swanzey NH 03446,False
Adult Lacrosse Pickup - Fieldhouse at Homestead Mills,10/06/2026,08:00 PM,10/06/2026,09:00 PM,False,"Pickup-style lacrosse, adult/college/HS. $15 drop-in or $80 for the 8-week Fall session (Sept 22-Nov 10 2026). Contact: (603) 338-0064",2 South Winchester St Swanzey NH 03446,False
Men's Pickup Box Lacrosse - NH Sportsplex,09/28/2026,08:00 PM,09/28/2026,10:00 PM,False,"Monday-night pickup box lacrosse, $15/session, BYO gear. Pauses once the Men's Box League season starts 10/26/2026. Contact: 603-641-1313 / info@nhsportsplex.com",68 Technology Dr Bedford NH 03110,False
```

Gaps to note for a real CSV: (1) an 8-week series is 8 rows per facility, not 1 — for every recurring entry in `LOCATIONS.md` a script would need to expand the weekday + date-range prose into a concrete list of dates; (2) several entries (e.g. the NH Sportsplex Men's Box Lacrosse *League*, ULAX programs) give a start date but no explicit clock time in Notes — that's missing data CSV import requires (`Start Time` isn't strictly required by Google, but omitting it likely produces an all-day-looking or ambiguous entry, which isn't what a real evening league session is); (3) the 1 MB file-size ceiling is unlikely to bind at this data's scale but would need checking once every venue's full season is enumerated.

### If using ICS (the format that actually supports the recurrence LOCATIONS.md describes)

The same Fieldhouse pickup game is naturally a single `VEVENT` with an `RRULE`, avoiding per-occurrence enumeration. A minimal, realistic example (weekly on Tuesdays, 8–9 PM Eastern, from Sept 22 through Nov 10, 2026 — `RRULE` syntax per RFC 5545, [datatracker.ietf.org/doc/html/rfc5545](https://datatracker.ietf.org/doc/html/rfc5545)):

```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//group-me//lacrosse-locations//EN
BEGIN:VEVENT
UID:fieldhouse-homestead-mills-pickup-fall2026@group-me
DTSTAMP:20260925T000000Z
DTSTART;TZID=America/New_York:20260922T200000
DTEND;TZID=America/New_York:20260922T210000
RRULE:FREQ=WEEKLY;BYDAY=TU;UNTIL=20261110T235959Z
SUMMARY:Adult Lacrosse Pickup - Fieldhouse at Homestead Mills
LOCATION:2 South Winchester St, Swanzey, NH 03446
DESCRIPTION:Pickup-style lacrosse\, adult/college/HS. $15 drop-in or $80
  for the 8-week Fall session. Contact: (603) 338-0064
END:VEVENT
END:VCALENDAR
```

This single `VEVENT` covers the whole 8-week run in one block (`UNTIL` bounds it to Nov 10, 2026), which is the structural advantage over CSV. The same still requires normalizing `LOCATIONS.md`'s prose into `DTSTART`/`DTEND`/`RRULE` fields, plus picking an IANA timezone (`America/New_York` for all MA/NH entries) since none is specified in the source data.

### If using the Calendar API (best fit for an actual automation)

Rather than generating a file at all, the same event maps directly onto an `events.insert` (or, for idempotent re-sync, `events.import`) request body: `summary`, `location`, `start`/`end` with `dateTime` + `timeZone`, and a `recurrence: ["RRULE:FREQ=WEEKLY;BYDAY=TU;UNTIL=20261110T235959Z"]` array — plus, for `events.import`, a stable `iCalUID` derived from the facility/program (e.g. `fieldhouse-homestead-mills-pickup-fall2026@group-me`) so re-running the sync updates rather than duplicates the event, mirroring the per-event stable-ID pattern already used for GroupMe bot message de-duplication in this repo's other research note. This still requires the same prose-to-structured-datetime parsing step as CSV/ICS, but removes the file-size limit, the manual click-through, and the need to hand-enumerate individual occurrences.

## Update / Synchronization Semantics (can we update, or only create?)

- **CSV/ICS file import (consumer UI) has no documented update/matching behavior at all.** Neither [support.google.com/calendar/answer/37118](https://support.google.com/calendar/answer/37118?hl=en) nor [Fix problems with importing](https://support.google.com/calendar/answer/45654?hl=en) says anything about re-importing a file that contains events already on the calendar — no mention of matching, merging, skipping, or overwriting existing events. The reasonable reading is that file import is a **pure "add" operation**: re-importing the same CSV/ICS is very likely to create duplicate events rather than update the originals, since nothing in Google's docs describes a matching key for this path. **File-based import (CSV or ICS) is therefore not a synchronization mechanism** — it has no update or delete story, only "add more events." This matches this task's premise that synchronization may be out of scope for import files specifically.
- **The Calendar API does support true updates — but via `events.update`/`events.patch`, not by re-calling `events.import`.** [developers.google.com/workspace/calendar/api/v3/reference/events/update](https://developers.google.com/workspace/calendar/api/v3/reference/events/update) confirms `events.update` modifies an existing event in place, keyed by `eventId` (Google's own event ID, not `iCalUID`), replacing the whole event resource ("does not support patch semantics and always updates the entire event resource" — use `events.patch` instead for partial field updates, per the same reference family).
- **Whether re-calling `events.import` itself with a duplicate `iCalUID` updates or duplicates the event is NOT confirmed by Google's own docs.** [developers.google.com/workspace/calendar/api/v3/reference/events/import](https://developers.google.com/workspace/calendar/api/v3/reference/events/import) documents `iCalUID` as required but is silent on repeated-call behavior — no wording about matching, overwriting, erroring, or duplicating on a second `import` call with the same `iCalUID`. Do not assume `events.import` is an upsert without testing it directly.
- **The documented, safe way to build a real sync loop**: `events.list` supports filtering by an event's `iCalUID` directly — its reference page states the `iCalUID` parameter lets a caller "search for an event by its iCalendar ID" ([developers.google.com/workspace/calendar/api/v3/reference/events/list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)). So the reliable pattern for this repo's use case is: for each `LOCATIONS.md`-derived event, deterministically generate its `iCalUID` (e.g. from facility + program + season, mirroring the GroupMe `source_guid` pattern already documented in the sibling research note) → call `events.list` filtered on that `iCalUID` → if found, call `events.update`/`events.patch` on the returned `eventId`; if not found, call `events.insert` (or `events.import`) to create it. This gives genuine create/update/delete sync semantics, which neither CSV nor ICS file import provides on its own.

## Open Questions / Unverified

- **Timezone handling for CSV import**: no primary-source page fetched documents a per-row timezone column or override for CSV; the only guidance found ([support.google.com/calendar/answer/45654](https://support.google.com/calendar/answer/45654?hl=en)) is the generic instruction to make sure "the time zone in Google Calendar matches the time zone in the original calendar application," which implies CSV-imported times are taken at face value in whatever timezone the destination calendar/account is set to — not independently confirmed.
- **Whether `All Day Event` values are case-sensitive** (`True`/`False` exactly, vs. `true`/`false`/`TRUE`) is not specified on the pages fetched.
- **Row-count limits within the 1 MB CSV/ICS size cap** are not documented — only the byte-size ceiling is stated; how many `LOCATIONS.md`-derived events that translates to in practice wasn't tested.
- **Whether a well-formed `RRULE` in an imported `.ics` file reliably produces a true single recurring series (vs. being expanded/flattened) through the consumer Import & Export UI specifically** is not explicitly guaranteed by any page fetched — [support.google.com/calendar/answer/45654](https://support.google.com/calendar/answer/45654?hl=en) only explains the *failure* case (a source app that itself exported without an `RRULE`). This is a reasonable inference from how `.ics`/RFC 5545 recurrence is designed to work, and is consistent with the Calendar API docs' explicit RFC 5545 recurrence support, but it is not a claim stated in Google's own words for the import-UI path specifically.
- **Whether Google silently changed the CSV header spec or import policy at some point in the past** (the premise floated in this task's brief, based on older community reports of CSV import being restricted) could not be assessed historically — this research only establishes the *current* (2026-09-25) state of the live help pages, not a change history. No deprecation notice or "CSV import is being phased out" language was found on any page fetched.
- **CSV import from generic/hand-built CSVs vs. only CSVs re-exported by name-brand calendar apps**: [support.google.com/calendar/answer/45654](https://support.google.com/calendar/answer/45654?hl=en) mentions Outlook/Apple/Yahoo Calendar only in the context of troubleshooting re-exports when an import fails, not as a hard whitelist restricting CSV import to files produced by those specific applications; a hand-built CSV matching the documented header spec appears to be supported, but this wasn't tested end-to-end with an actual import attempt (out of scope for this research).
