# Calendar Subscribe Links: Google Calendar / Outlook One-Click ICS Mechanics

## Summary

Checked directly against each provider's own current help pages, **neither Google Calendar nor Outlook/Outlook.com documents a one-click "subscribe" deep-link URL scheme in their own official support docs.** For Google, the only officially documented path to add a public `.ics`/webcal feed is the manual **Settings → Add other calendars → From URL** flow, described on [support.google.com/calendar/answer/37100](https://support.google.com/calendar/answer/37100?hl=en&co=GENIE.Platform%3DDesktop) ("Use a link to add a public calendar"), which — despite its heading — turns out to be the *same* manual "enter the URL of the published calendar" flow, not a webmaster-constructible deep link. The widely-used `https://www.google.com/calendar/render?cid=<url>` (or `calendar.google.com/calendar/render?cid=`) trick exists and is real-world functional, but it is **not documented anywhere on support.google.com** — it was reverse-engineered from Google's own web-client JavaScript bundle, as stated explicitly (and only) by a third-party technical source ([Simon Willison's TIL](https://til.simonwillison.net/ics/google-calendar-ics-subscribe-link): "As far as I can tell this isn't documented anywhere, but it is possible"). For Outlook/Outlook.com, the only officially documented path is likewise manual: **Calendar → Add calendar → Subscribe from web → paste URL → Import**, per [support.microsoft.com's "Import or subscribe to a calendar in Outlook.com or Outlook on the web"](https://support.microsoft.com/en-us/office/import-or-subscribe-to-a-calendar-in-outlook-com-or-outlook-on-the-web-cff1429c-5af6-41ec-a5b4-74f2c278e98c) page; no documented deep-link parameter (e.g. an `outlook.live.com`/`outlook.office.com` URL that pre-fills and auto-subscribes an ICS URL) was found on any Microsoft-owned domain.

On refresh cadence, **Microsoft's own docs do state an approximate number** — the same support page says updates "can take more than 24 hours, although updates should happen approximately every 3 hours" (Outlook.com) and "approximately every 6 hours" (Outlook on the web) — while **Google's docs are silent**: no page on support.google.com found in this research states any refresh interval, approximate or otherwise, for a calendar added via "From URL." A number ("less than once every 24 hours") does circulate for Google in third-party developer sources, but this is explicitly flagged below as *not* from Google's own documentation.

On `webcal://` vs `https://`, no official Google or Microsoft support page addresses the distinction directly; the only clearly authoritative source found is IANA's own [URI Schemes registry](https://www.iana.org/assignments/uri-schemes/uri-schemes.txt), which lists `webcal` with **Provisional** (not Permanent) status, referencing Dave Thaler — i.e. `webcal://` is a registered-but-provisional scheme, not a fully standardized one, which is consistent with it being handled inconsistently across browsers/OSes.

**Practical implication for this repo's planned subscribe UI**: since no provider documents a reliable one-click deep link, the "Subscribe" buttons should be built as best-effort convenience links (the widely-used but undocumented `render?cid=` pattern for Google can still be offered as a "try this" link, clearly not guaranteed) alongside — not instead of — a always-available "copy the `https://natenite.net/events.ics` URL and paste it into your calendar app" fallback, since that fallback is the *only* mechanism either provider actually documents.

## Findings

### 1. Google Calendar: one-click deep-link vs. documented manual path

- **The only documented mechanism** is on [support.google.com/calendar/answer/37100](https://support.google.com/calendar/answer/37100?hl=en&co=GENIE.Platform%3DDesktop) ("Subscribe to someone else's calendar"), under the heading **"Use a link to add a public calendar"**:
  - "You can only add a calendar with a link if the other person's calendar is public."
  - Steps, quoted verbatim: "On your computer, open Google Calendar." → "On the left, next to 'Other calendars,' click Add other calendars and then From URL." → "Enter the URL of the published calendar." → "Click Add calendar. The calendar displays on the left, under 'Other calendars.'"
  - Despite the heading name ("Use a link to add a public calendar"), this section does **not** describe a specific constructible URL format a webmaster could hand a visitor for one-click subscription — it describes the end user manually pasting a calendar's published URL into Google Calendar's own "From URL" settings field. This was confirmed by reading the section in full.
  - The page also states subscribing "From URL" is desktop/web-only: "To subscribe to a new calendar, you must use a computer web browser. You can't subscribe to a calendar in the Google Calendar app for Android, iPhone, or iPad."
- **The `render?cid=` trick is real but undocumented by Google.** Searching support.google.com directly (both via site-restricted web search and by reading the relevant help pages) turned up no page describing a `calendar.google.com/calendar/render?cid=` or `google.com/calendar/render?cid=` deep-link parameter. The pattern (`https://www.google.com/calendar/render?cid=webcal://<url>`, which drops a signed-in user into a "subscribe to this calendar?" confirmation UI) is documented only by third parties who explicitly say so:
  - [Simon Willison's TIL](https://til.simonwillison.net/ics/google-calendar-ics-subscribe-link) states outright: "As far as I can tell this isn't documented anywhere, but it is possible," and that the pattern was found by reading Google's own web-client bundle rather than any help page.
  - A live Google Issue Tracker bug, [issuetracker.google.com/issues/442619500](https://issuetracker.google.com/issues/442619500) ("`/render?cid=` endpoint fails to add external calendars"), shows the endpoint is known to Google engineering (it's tracked as a bug against real behavior) but this is a bug report, not documentation — it does not constitute an official specification of the URL's contract, and this research did not confirm its content in detail (see Open Questions).
  - **Conclusion for this question: not officially documented.** Treat `render?cid=` as an unsupported-but-functional convenience link, not a guaranteed API.
- **Public calendar prerequisite**: per [support.google.com/calendar/answer/37083](https://support.google.com/calendar/answer/37083?hl=en) ("Create & manage a public Google calendar"), any link-based add (documented or the undocumented `cid=` trick) requires the target calendar/feed to be public in the first place — not relevant to this repo's use case since `events.ics` is already a public static file with no auth, but confirms the "must be public" precondition stated in `answer/37100` is consistent across Google's own docs.
- **webcal:// vs https:// for Google's documented "From URL" field**: [support.google.com/calendar/answer/37100](https://support.google.com/calendar/answer/37100?hl=en&co=GENIE.Platform%3DDesktop) does not specify a required URL scheme at all — it only says "Enter the URL of the published calendar" with no protocol guidance one way or the other. No other Google support page fetched in this research ([answer/37083](https://support.google.com/calendar/answer/37083?hl=en), [answer/37648](https://support.google.com/calendar/answer/37648?hl=en) "Sync your calendar with computer programs") addresses this either. **Google's own docs are silent on whether a plain `https://` URL is acceptable versus requiring `webcal://`** — this is a real gap, not an oversight in this research (see Open Questions for what's known informally vs. confirmed).

### 2. Outlook / Outlook.com / Outlook on the web

- **The only documented mechanism** is on [support.microsoft.com's "Import or subscribe to a calendar in Outlook.com or Outlook on the web"](https://support.microsoft.com/en-us/office/import-or-subscribe-to-a-calendar-in-outlook-com-or-outlook-on-the-web-cff1429c-5af6-41ec-a5b4-74f2c278e98c) page:
  - Quoted steps: "Select Calendar from the navigation pane and click Add calendar." → "Select Subscribe from web." → "Enter the URL for the calendar." → "Select Import."
  - The same page distinguishes **importing** (a one-time snapshot, no auto-refresh: "When you import an .ics file, you get a snapshot of the events at the time of import, and your calendar doesn't refresh the imported events automatically") from **subscribing** (a live connection: "Subscribing to an online calendar connects it to your calendar, and whenever the owner of a calendar you've subscribed to makes changes to the events, Outlook updates your calendar").
  - The related page [support.microsoft.com/en-us/office/add-a-calendar-in-outlook-com-or-outlook-on-the-web](https://support.microsoft.com/en-us/office/add-a-calendar-in-outlook-com-or-outlook-on-the-web-6641b635-2797-42ce-a500-597eaef0fd19) confirms the same "Subscribe from web" flow and notes generically that "Websites for theaters, sports teams, and schools often have an 'Add to calendar' link that you can use to download an iCal" — i.e. it acknowledges third-party "add to calendar" links exist as a *concept*, but does not itself define or document a deep-link URL parameter format for Outlook to consume one automatically.
- **No documented one-click deep link found on any Microsoft-owned domain** (support.microsoft.com or learn.microsoft.com) that takes an ICS/webcal URL as a query parameter and auto-subscribes it. A community Microsoft Q&A thread exists asking for exactly this ("Direct Link for ICS Calendar Subscription in Outlook Calendar," [learn.microsoft.com/en-us/answers/questions/4531670](https://learn.microsoft.com/en-us/answers/questions/4531670/direct-link-for-ics-calendar-subscription-in-outlo)) — the mere existence of that unanswered community question is itself weak corroborating evidence that no official mechanism is documented, but a user-forum thread is not a primary source and was not relied on for any factual claim here.
- **Desktop Outlook (Windows/Mac) — brief, secondary note**: [support.microsoft.com/en-us/office/introduction-to-publishing-internet-calendars](https://support.microsoft.com/en-us/office/introduction-to-publishing-internet-calendars-a25e68d6-695a-41c6-a701-103d44ba151d) confirms desktop Outlook supports "Internet Calendars" (`.ics`-based) as a distinct concept from Outlook.com/Outlook-on-the-web subscriptions, and states that subscribers "see the latest information automatically" once subscribed, but does not itself state a refresh interval or a deep-link mechanism. Community/forum sources (not official docs, and not cited here as fact) describe a desktop-only "Update Limit" checkbox (Outlook desktop → account settings → Internet Calendars) that, when unchecked, refreshes the calendar on every manual Send/Receive rather than waiting for a publisher-recommended interval — this is mentioned only as a pointer for future investigation, not as a documented fact.
- **webcal:// vs https:// for Outlook**: none of the Outlook/Outlook.com pages fetched ([import-or-subscribe...](https://support.microsoft.com/en-us/office/import-or-subscribe-to-a-calendar-in-outlook-com-or-outlook-on-the-web-cff1429c-5af6-41ec-a5b4-74f2c278e98c), [add-a-calendar...](https://support.microsoft.com/en-us/office/add-a-calendar-in-outlook-com-or-outlook-on-the-web-6641b635-2797-42ce-a500-597eaef0fd19), [introduction-to-publishing-internet-calendars](https://support.microsoft.com/en-us/office/introduction-to-publishing-internet-calendars-a25e68d6-695a-41c6-a701-103d44ba151d)) state a required or preferred URL scheme; all refer generically to "the URL of the calendar" / "the web address of the calendar."

### 3. Refresh / re-poll interval — documented vs. undocumented

- **Microsoft documents an approximate interval, in its own words**, on the same "Import or subscribe" page:
  - Under the Outlook.com-specific guidance: "When you subscribe to a calendar, your calendar will automatically refresh if the other calendar is updated. This can sometimes take more than 24 hours," and, in the page's import-vs-subscribe comparison: "This update can take more than 24 hours, although updates should happen approximately **every 3 hours**."
  - Under the Outlook-on-the-web-specific guidance: "Whenever events change on an iCal, it can take more than 24 hours for Outlook on the web to update your calendar," with the comparable comparison-section figure stated as approximately **every 6 hours**.
  - Net: Microsoft's own page gives two different approximate numbers (3 hours vs. 6 hours) depending on which product surface (Outlook.com vs. Outlook on the web) the text is describing, with an explicit caveat both times that the true worst case "can take more than 24 hours." Both figures come from the single page cited above — no other Microsoft page fetched in this research restates or reconciles the discrepancy.
- **Google's own docs are silent.** No page fetched from support.google.com in this research ([answer/37100](https://support.google.com/calendar/answer/37100?hl=en&co=GENIE.Platform%3DDesktop), [answer/37083](https://support.google.com/calendar/answer/37083?hl=en), [answer/37648](https://support.google.com/calendar/answer/37648?hl=en)) states any refresh/polling cadence for a calendar added via "From URL." This silence should be reported as a finding, not filled in with a guess.
  - A number does circulate in third-party developer material — e.g. the figure "less than once every 24 hours" appears in independent write-ups about Google Calendar ICS polling behavior — but this is **explicitly not from Google's own documentation** and is flagged here only as a third-party claim, not a fact to rely on.

### 4. `webcal://` vs `https://` (secondary)

- **IANA's own registry is the clearest authoritative source found.** [iana.org/assignments/uri-schemes/uri-schemes.txt](https://www.iana.org/assignments/uri-schemes/uri-schemes.txt) lists `webcal` with status **Provisional** (not Permanent), reference "[Dave_Thaler]" — i.e. `webcal` is a registered URI scheme, but only at IANA's lower "Provisional" registration tier, not the fully standardized "Permanent" tier that schemes like `http`/`https` hold. This is consistent with `webcal://` being treated as a legacy/best-effort convention (historically associated with Apple iCal) rather than a scheme every browser/OS is obligated to handle.
- Neither Google's nor Microsoft's own support pages fetched in this research take a documented position recommending one scheme over the other, or warning about inconsistent OS/browser handling of `webcal://` — this secondary question is simply not addressed in either provider's own docs, based on the pages checked.
- **Practical reading for this repo**: since (a) Google's documented "From URL" field says only "enter the URL," (b) Outlook's documented "Subscribe from web" field says only "enter the URL," and (c) `webcal://` itself is only Provisional at IANA, the safer choice for `events.ics`'s public URL is the plain `https://natenite.net/events.ics` form already in use — it is unambiguously supported by every documented manual-paste flow, whereas `webcal://` support is not documented as guaranteed by either provider and carries acknowledged inconsistent real-world browser handling (this last point is a reasonable inference from the Provisional IANA status plus the total silence on scheme choice in both providers' docs, not a directly stated claim from any single source).

## Open Questions / Unverified

- **Exact current behavior of `render?cid=`** (whether it still works, what confirmation UI it shows, whether it requires the visitor to be signed into a Google account first) was not independently tested in this research — only documented as "exists, works per third-party report, not officially documented." The linked Google Issue Tracker bug ([issuetracker.google.com/issues/442619500](https://issuetracker.google.com/issues/442619500)) could not be read in detail (the fetch only returned a sign-in page shell, not the ticket body), so its exact content/status is unconfirmed — it's cited here only as evidence the endpoint is known to Google, not for any claim about its current reliability.
- **Whether Google's "From URL" field silently accepts `webcal://` and rewrites it, versus requiring `https://`/`http://` directly**, is not stated in any support.google.com page fetched. Third-party/community sources (Google Calendar Community forum threads, not cited as fact here) suggest both forms work in practice, but this was not confirmed against an official Google page and should be verified empirically (e.g. by testing the actual `events.ics` URL) before being stated as fact in any user-facing copy.
- **The 3-hours-vs-6-hours discrepancy in Microsoft's own single support page** (Outlook.com vs. Outlook on the web) is reported here exactly as written on that page — it was not possible to determine from that page alone whether these are genuinely two different systems with two different polling cadences, or an inconsistency/leftover from an edit. Treat both numbers as "approximately, per Microsoft's own words," not as a precise SLA.
- **Desktop Outlook's actual refresh mechanics** ("Update Limit" checkbox, publisher-recommended interval headers, Send/Receive-triggered refresh) were only found in Microsoft Q&A community threads and forum posts, not on an official support.microsoft.com or learn.microsoft.com documentation page — this entire sub-topic is unconfirmed against a primary source and is flagged here as a pointer for follow-up research only, consistent with this question being explicitly secondary in scope.
- **Whether any provider has since (post-fetch) changed these pages** — this is a live, editable support page for both providers; the quotes above reflect the page content as fetched on 2026-09-27 and could change without notice.
- **iCloud/Apple Calendar's role in `webcal://`'s history** was mentioned informally (webcal was devised for Apple's iCal) but not independently verified against an Apple-owned primary source in this research, since Apple was out of scope for this issue's four questions.
