# Public Calendar Website Options

## Summary

For a public, read-only, no-login calendar site sourced from `LOCATIONS.md`, the strongest fit — verified directly against each tool's own docs/repo — is a **static-file pipeline: a script converts `LOCATIONS.md` into a single `.ics` file → that `.ics` file is hosted as a static asset (e.g. alongside the site on GitHub Pages) → a plain HTML page embeds FullCalendar's own first-party `@fullcalendar/icalendar` plugin, which is documented (and confirmed via the npm registry) to be **MIT-licensed** and built specifically to "display events from a public iCalendar feed" by URL, no custom backend required ([fullcalendar.io/docs/icalendar](https://fullcalendar.io/docs/icalendar); [registry.npmjs.org/@fullcalendar/icalendar](https://registry.npmjs.org/@fullcalendar/icalendar/latest)). This beats the Google Calendar embed option because Google's own embed docs confirm it offers only two customization knobs — iframe dimensions and on/off navigation buttons ([support.google.com/calendar/answer/41207](https://support.google.com/calendar/answer/41207?hl=en)) — with no documented way to filter/group by location or brand the page, whereas a FullCalendar-based static page is fully under this project's control for layout, filtering, and branding. FullCalendar's *core* is MIT ([fullcalendar.io/license](https://fullcalendar.io/license); confirmed directly against the `fullcalendar` npm package's `license` field, also `MIT`), and the ICS plugin specifically is MIT too (not one of FullCalendar's "Premium/Scheduler" packages, which do carry a separate commercial/non-commercial license) — so no premium license purchase is needed for this use case. The whole pipeline can run for $0/month on GitHub Pages (free static hosting for public repos, confirmed via GitHub's own docs) with no server, database, or ongoing infrastructure — the only unsolved piece, carried over unchanged from this project's own prior research, is turning `LOCATIONS.md`'s hand-written prose schedules into structured `DTSTART`/`DTEND`/`RRULE` data in the first place.

## Findings

### 1. Google Calendar public embed (zero-code option)

Checked directly against Google's own support pages, three related but distinct steps:

- **Making a calendar public** ([support.google.com/calendar/answer/37083](https://support.google.com/calendar/answer/37083?hl=en)): Settings → select the calendar under "Settings for my calendars" → check "Make available to public" → OK. Google's own wording: "If this website is searchable, people can find your calendar in search results," and a public calendar can be synced with other applications or subscribed to. This setting is computer/desktop-only ("You can only edit Google Calendar sharing settings from a computer, not the mobile app"), and for Google Workspace accounts "your domain's administrator may restrict your sharing settings." A change to this setting "may take up to 4 hours to take effect."
- **Access level for public visibility** ([support.google.com/calendar/answer/37082](https://support.google.com/calendar/answer/37082?hl=en)): the "Access permissions for events" dropdown controls how much detail public/shared viewers see, ranging from **See only free/busy (hide details)** up through **See event details**, **Make changes**, and **Make changes and manage sharing** — for a public read-only events calendar, "See event details" is the relevant level.
- **Embedding** ([support.google.com/calendar/answer/41207](https://support.google.com/calendar/answer/41207?hl=en)): the calendar must already be public — Google's own text: "Your calendar is only visible to people you share it with. To make your calendar visible to everyone, make your calendar public." From there: Settings → select the calendar → **Integrate calendar** → under "Embed code," click **Customize** → copy the generated `<iframe>` code and paste it into your site. Like the public setting, this is a computer-only workflow (no embed-code generation from the mobile app).
- **Documented customization is minimal.** The only two customization controls the support page itself describes are: (1) **dimensions** — "Select dimensions where the width and height are each at least 500" (i.e. a 500×500px iframe floor), and (2) **navigation buttons** — turning them off means "people can only use keyboard shortcuts to navigate your calendar." No other customization (default view, colors/branding, title visibility, filtering by calendar/location, language) is described on this page. (Google's actual "Customize" dialog is known from general use to expose more toggles than the support article documents in words — e.g. background color, title, default view — but since this research is scoped to what Google's own docs state, only the two documented controls above should be treated as confirmed; see Open Questions.)
- **Visitor interaction**: visitors can click "Add to Google Calendar" at the embedded calendar's bottom-left to subscribe it to their own calendar — this is the one documented interactive/self-service feature.
- **Limitations for this project's use case**: the embed is a single calendar view (day/week/month), branded as Google Calendar chrome, with no documented mechanism to filter events by facility/location, group leagues vs. pickup games, or apply this project's own visual identity — it is literally an iframe of the Google Calendar UI, not a custom page. It also requires maintaining the source-of-truth events *inside* an actual Google Calendar (populated via the CSV/ICS import or Calendar API paths already documented in `docs/research/google-calendar-csv-import.md`), which is an extra moving part beyond a static `.ics` file if the eventual home for this data is a static site.

### 2. JavaScript calendar UI libraries

Three options were checked directly against their own repos/docs/license files.

**FullCalendar** ([fullcalendar.io](https://fullcalendar.io/) / [github.com/fullcalendar/fullcalendar](https://github.com/fullcalendar/fullcalendar))
- Described in its own README as a "full-sized drag & drop event calendar in JavaScript," with 20.7k GitHub stars and framework connectors for React, Angular, and Vue, plus a plain-JS "Standard Bundle."
- **License, confirmed precisely**: the core/standard packages and the `fullcalendar` bundle are **MIT** — confirmed both via [fullcalendar.io/license](https://fullcalendar.io/license) ("The non-premium plugins and the `fullcalendar` bundle are released under the MIT license... permits a wide range of use, including free use in commercial projects") and directly via the npm registry's `license` field for the `fullcalendar` package itself (`"MIT"`, version `7.1.0`, at [registry.npmjs.org/fullcalendar/latest](https://registry.npmjs.org/fullcalendar/latest)). **FullCalendar Premium** (the `fullcalendar-scheduler` bundle: resource/timeline views, drag-and-drop scheduling across resources) is under a separate, more restrictive license: for-profit commercial use requires a purchased commercial license; non-profits (excluding universities/government) may use a free Creative Commons BY-NC-ND 4.0 non-commercial license; fully open-source AGPLv3 projects may use it under AGPLv3 (as of FullCalendar v7); anyone using it without a valid `schedulerLicenseKey` gets a visible "unlicensed" warning banner. None of the Premium/Scheduler features (resource views, cross-resource drag-and-drop) are needed for a simple public read-only events list, so the MIT-licensed core is sufficient here.
- **Rendering model**: FullCalendar is a pure client-side rendering library — it does not require a backend of its own. It supports a "Standard Bundle" usable via plain `<script>` tags with no build step (confirmed via [fullcalendar.io/docs/initialize-globals](https://fullcalendar.io/docs/initialize-globals), which documents a jsDelivr CDN URL like `https://cdn.jsdelivr.net/npm/fullcalendar@7.1.0/all/global.js`), as well as npm-installable per-feature plugin packages for bundler-based projects.
- **ICS support is first-party and documented**: see the dedicated ICS section below.

**Schedule-X** ([github.com/schedule-x/schedule-x](https://github.com/schedule-x/schedule-x) / [schedule-x.dev](https://schedule-x.dev/))
- Self-described in its own repo as "the modern JavaScript event calendar... a modern alternative to fullcalendar and react-big-calendar," with responsive design and multi-framework support (React, Angular, Vue, Svelte, Preact, or plain JS).
- **License**: **MIT** (confirmed in the repo's own license metadata: "Copyright 2023 - present, Tom Österlund").
- **Actively maintained**: 2.6k stars, 181 forks, 1,098 commits on `main`, active open issues/PRs as observed directly on the repo page at research time (2026-09-25).
- **Rendering model / build requirements**: client-side only, no backend; the repo is an npm-package monorepo (Rollup/Vite/Lerna/Nx configs visible in the repo root) — this is an npm-and-bundler library, not a drop-in CDN `<script>` tag like FullCalendar's global build; no plain-`<script>`-tag/CDN usage path was found documented.
- **ICS support**: has a first-party `@schedule-x/ical` plugin (`createIcalendarPlugin`), documented at [schedule-x.dev/docs/calendar/plugins/ical](https://schedule-x.dev/docs/calendar/plugins/ical) — but unlike FullCalendar's plugin, it takes a **raw iCalendar string** passed directly at initialization (`data: 'BEGIN:VCALENDAR...'`), not a feed URL to fetch — so the calling code must fetch the `.ics` file's text itself first. The plugin's own docs also state it "assumes UTC timezone for all events" and advise skipping timezone configuration when using it — a real caveat for events that should display in `America/New_York`. No live-refresh/re-fetch mechanism is documented; it reads as a one-time data load, similar to FullCalendar's ICS plugin behavior.

**TOAST UI Calendar** ([github.com/nhn/tui.calendar](https://github.com/nhn/tui.calendar)) — checked and **ruled out**
- This is a commonly recommended FullCalendar alternative in third-party roundups, but checking the repo directly (not a blog post) shows it is **archived**: "This repository was archived by the owner on Sep 2, 2026. It is now read-only." It is MIT-licensed and was a full-featured calendar (day/week/month views, drag-and-drop, milestone/task scheduling, React/Vue wrappers) maintained by NHN Cloud, but it no longer meets the "actively-maintained" bar this research requires, so it's flagged here specifically as a caution against relying on third-party "best calendar libraries" lists without checking the repo itself.

### 3. Static site generators / hosting for a static-data project

Since `LOCATIONS.md` is hand-maintained and low-volume (not a live database), a plain static HTML+JS page — no site generator or framework required — hosted on any of the following is sufficient. All three were checked against their own docs:

- **GitHub Pages** ([docs.github.com — About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages) and [github-pages-limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)): "a static site hosting service that takes HTML, CSS, and JavaScript files straight from a repository on GitHub, optionally runs the files through a build process, and publishes a website" — a build step (e.g. Jekyll) is optional, not required; "GitHub Pages publishes any static files that you push to your repository." Free for public repositories on the free GitHub plan (private-repo Pages requires GitHub Pro/Team/Enterprise). Documented usage limits: a **soft 100 GB/month bandwidth limit**, a **soft 10 builds/hour limit** (waived if publishing via a custom GitHub Actions workflow), a **1 GB published-site size cap**, and a **10-minute deployment timeout**. Custom domains are supported. Server-side languages (PHP/Ruby/Python) are explicitly not supported — irrelevant here since the pipeline is pure static HTML/JS/`.ics`.
- **Cloudflare Pages** ([developers.cloudflare.com/pages](https://developers.cloudflare.com/pages/) and [.../platform/limits](https://developers.cloudflare.com/pages/platform/limits/)): supports Git-based deploys or direct static-asset "Direct Upload." Free plan: 500 builds/month, up to 100 projects/account, 20,000 files per site (25 MiB per asset) — no bandwidth cap documented as a hard limit in the fetched content. Cloudflare's own docs note they now steer *new* projects toward "Workers" more broadly, but Pages remains documented and available.
- **Netlify** ([docs.netlify.com/get-started](https://docs.netlify.com/get-started/) and [netlify.com/pricing](https://www.netlify.com/pricing/)): explicitly supports a zero-build static deploy via drag-and-drop at `app.netlify.com/drop` ("You don't have to build your project first... Netlify will detect your framework, run the build, and publish the result for you") as well as Git-based auto-deploy. The free "Starter" plan is "$0 forever" but is now run on a **credit-based** system (300 credits/month) rather than flat GB/build-minute quotas — e.g. a production deploy costs 15 credits and bandwidth costs 20 credits/GB, which at 300 credits is roughly ~15 GB of bandwidth or ~20 deploys per month if nothing else is used. For a low-traffic hobby calendar page this is very unlikely to bind, but it's a materially different pricing model from GitHub Pages' flat soft-cap and worth knowing going in.

**Net for this project**: any of the three works for $0/month; GitHub Pages is the simplest fit since the repo is already on GitHub — no separate account/service to provision, and the docs confirm plain static files (including a hand-generated `.ics` file) publish as-is with no build pipeline required.

### 4. iCalendar (.ics) feed readers/renderers specifically

The sibling research (`docs/research/google-calendar-csv-import.md`) already covers *producing* `.ics` output (RRULE syntax, RFC 5545 structure) — this section covers *rendering* an existing `.ics` feed as a calendar view.

- **FullCalendar's own first-party `@fullcalendar/icalendar` plugin** ([fullcalendar.io/docs/icalendar](https://fullcalendar.io/docs/icalendar)) is the most directly relevant, purpose-built option: its npm description (confirmed via the registry) is literally "Display events from a public iCalendar feed." Usage is exactly two extra packages (`@fullcalendar/icalendar` and its parsing dependency, `ical.js`) plus an events-source config of `{ url: 'https://mywebsite/icalendar-feed.ics', format: 'ics' }` — no server-side code. FullCalendar's own docs' example:
  ```js
  import { Calendar } from 'fullcalendar'
  import dayGridPlugin from 'fullcalendar/daygrid'
  import iCalendarPlugin from '@fullcalendar/icalendar'

  var calendar = new Calendar(calendarEl, {
    plugins: [dayGridPlugin, iCalendarPlugin],
    events: { url: 'https://mywebsite/icalendar-feed.ics', format: 'ics' }
  })
  calendar.render()
  ```
  Confirmed browser-usable without a bundler too: the published package ships a `global.js` UMD build (visible directly on jsDelivr's listing for `@fullcalendar/icalendar@7.1.0`), and its dependency `ical.js` is MPL-2.0-licensed (a weak/file-level copyleft license — distinct from FullCalendar's own MIT, but not a practical obstacle for using it as an unmodified dependency) and also ships browser-ready ESM/CJS builds per jsDelivr's own package page. **Documented limitation**: "Your iCalendar feed will be queried upon calendar load and will not be queried after" — i.e., it's a one-time fetch per page load, not a live-polling feed; a page revisit re-fetches it, but within a single open tab it won't pick up mid-session changes unless the code explicitly calls `refetchEvents()`. For a low-frequency, hand-maintained data source like `LOCATIONS.md`, this "re-fetch on page load" behavior is entirely adequate.
- FullCalendar's own docs page for this plugin does **not** state whether `RRULE`-based recurring events inside the `.ics` feed are correctly expanded into a repeating series in the rendered calendar (this is a gap consistent with a similar unconfirmed-recurrence caveat already flagged in the sibling CSV/ICS research) — see Open Questions.
- **Schedule-X's `@schedule-x/ical` plugin** is the other purpose-built option found (see library comparison above) — functionally similar but takes a raw ICS string rather than a URL, and explicitly assumes UTC (a real wrinkle for `America/New_York` events).
- No other actively-maintained, purpose-built "just render an ICS feed" widget (as opposed to a full calendar app framework) turned up from a primary-source repo/docs check; general-purpose "roundup" results (e.g. generic "ics-calendar" GitHub topic pages) were not used as cited sources per this research's constraints.

### 5. Hosting cost/complexity comparison

| Path | Backend/server needed? | Rebuild/redeploy needed on `LOCATIONS.md` change? | Free tier | Primary source |
|---|---|---|---|---|
| **Google Calendar embed** | No server, but a live Google Calendar must be populated and kept in sync (via CSV/ICS import or the Calendar API, per the sibling research) | No redeploy of the *embed* itself — the iframe reflects the calendar live — but every event change requires a re-import or API call into Google Calendar | Free (personal Google account) | [support.google.com/calendar/answer/41207](https://support.google.com/calendar/answer/41207?hl=en), [.../37083](https://support.google.com/calendar/answer/37083?hl=en) |
| **Static HTML + FullCalendar (or Schedule-X) reading a static `.ics` URL** | No server/database — pure static files | The `.ics` file itself must be regenerated whenever `LOCATIONS.md` changes and re-deployed (or hosted at a stable URL that gets overwritten in place); the HTML/JS page itself never needs to change, only the `.ics` file it points to. Because the ICS plugin fetches on every page load (not build time), simply overwriting the hosted `.ics` file is enough — no full site rebuild is required, only re-uploading that one file. | Free (GitHub Pages / Cloudflare Pages / Netlify, per docs above) | [docs.github.com — GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [fullcalendar.io/docs/icalendar](https://fullcalendar.io/docs/icalendar) |

The static-HTML path is materially simpler to operate: there's no OAuth/API credential to manage (unlike the Calendar-API path from the sibling research), and updating events is "regenerate one `.ics` file and push it," not "run an import wizard" or "call an authenticated API."

## Recommendation for This Project

Given `LOCATIONS.md`'s actual shape — facility name, address, a `Fields` indoor/outdoor tag, and a free-text `Notes` field carrying the real schedule info (e.g. "Tuesdays, 8–9 PM... Fall 2026: Sept 22 – Nov 10, 2026") — and this project's own prior research finding that `.ics`/RFC 5545 is the right format for expressing that as a recurring `VEVENT` with an `RRULE` (see `docs/research/google-calendar-csv-import.md`), a realistic minimal pipeline is:

1. **A script parses `LOCATIONS.md`'s Notes fields into structured event data** (facility, day-of-week, start/end time, season date range, cost) and emits a single `.ics` file — this is exactly the `VCALENDAR`/`VEVENT`/`RRULE` structure already worked out in the sibling research's "If using ICS" example (weekly `RRULE` with `UNTIL`, `America/New_York` `TZID`, one `VEVENT` per program/league rather than one row per occurrence).
2. **That `.ics` file is committed to this repo and published as a static file** — e.g. `https://<org>.github.io/group-me/events.ics` via GitHub Pages, which requires no build step and is free for a public repo (confirmed limits: 100 GB/month soft bandwidth cap, 1 GB site-size cap — both far beyond what a handful of lacrosse events needs).
3. **A small static `index.html` on the same GitHub Pages site embeds FullCalendar's core (MIT-licensed, CDN/global-bundle usable with no bundler) plus its first-party, also-MIT `@fullcalendar/icalendar` plugin**, pointed at that `events.ics` URL via `events: { url: '/events.ics', format: 'ics' }`. No backend, no database, no OAuth credentials, and re-publishing an event update is just "regenerate `events.ics`, commit, push" — the HTML page itself never needs to change.
4. This deliberately **skips the Google Calendar embed path** as the primary route (though it remains a viable fallback given how little effort it takes once a calendar is populated) because its own documented customization surface is limited to iframe size and nav-button visibility — no location filtering, no custom branding — and it requires standing up and maintaining a live Google Calendar as an intermediate system of record, which is one more moving part than "one static file."

**What's still unsolved**, and out of scope for this research: exactly as the sibling `google-calendar-csv-import.md` research already flagged, none of this addresses the actual parsing gap — turning `LOCATIONS.md`'s hand-written prose ("Tuesdays, 8–9 PM... Fall 2026: Sept 22 – Nov 10, 2026," "Monday nights 8–10 PM," "16-week league, Wed evenings Nov 13–Mar 18 (holiday breaks)") into structured `DTSTART`/`DTEND`/`RRULE` values is a real, unaddressed data-extraction problem, not a solved one, regardless of which rendering library or host is chosen downstream.

## Open Questions / Unverified

- **Google's full "Customize" embed dialog options beyond dimensions/navigation buttons.** The support page fetched documents only two controls in prose; the actual customize UI (known informally to include options like background color, default view, and title display) was not independently verified against Google's own written documentation and should not be assumed beyond what's stated here.
- **Whether FullCalendar's `@fullcalendar/icalendar` plugin correctly expands `RRULE` recurrence** (as opposed to only rendering non-recurring `VEVENT`s) is not explicitly stated on FullCalendar's own docs page for this plugin — this mirrors an identical open question already flagged in the sibling `google-calendar-csv-import.md` research about recurrence fidelity through Google's own ICS import path, and should be tested directly with a real recurring event before relying on it.
- **Cloudflare Pages' bandwidth limit** was not stated as a hard number in the fetched Cloudflare docs content (only build count, project count, and per-site file limits were found) — whether there's an unstated/soft bandwidth ceiling wasn't confirmed.
- **Whether a live-updating (auto-refreshing) calendar view is wanted at all.** Since `LOCATIONS.md` changes at human/editorial cadence (not continuously), the "fetch once per page load" behavior documented for both FullCalendar's and Schedule-X's ICS plugins is treated here as sufficient — but this assumption wasn't validated against any stated product requirement beyond what's implied by the task description.
- **Schedule-X's actual browser/CDN-without-bundler support** wasn't directly confirmed or denied in its own docs (only inferred from the presence of monorepo build tooling in the GitHub repo) — someone wanting to avoid a bundler entirely should verify this before choosing Schedule-X over FullCalendar, which does have a confirmed global/CDN build.
